Parte A

Antes de empezar

El problema en una frase

Hay una lista de clientes de un banco, observados mes a mes. Para cada cliente en diciembre de 2026 hay que dar un número entre 0 y 1: qué tan probable es que ese cliente haga su primera conversión en ese mes. Un número cercano a 1 significa "muy probable"; cercano a 0, "muy improbable".

No se pide adivinar sí o no. Se pide ordenar a los clientes de más a menos propensos. Por eso la competencia usa una métrica de orden y no de aciertos.

Cómo aprende una máquina

Se le entrega una tabla de ejemplos pasados donde ya se conoce la respuesta (train.csv, enero a noviembre). La máquina busca patrones entre las características de cada cliente y el resultado. Después se le entrega una tabla nueva donde la respuesta está oculta (test.csv, diciembre) y pide el número para cada fila. Esa herramienta que aprende los patrones se llama modelo.

La métrica: AUC y Gini

Analogía

Elige al azar un cliente que sí convirtió y otro que no. El AUC es la probabilidad de que el modelo le haya dado un puntaje más alto al que sí convirtió. Si adivina al azar, acierta la mitad de las veces (AUC = 0,5). Si ordena perfecto, siempre (AUC = 1).

El Gini es el mismo dato reescrito para que el azar valga 0: Gini = 2 × AUC − 1. Mueve el control para ver la relación.

Nuestros modelos están alrededor de un Gini de 0,25, es decir un AUC de 0,625. Es mejor que el azar, pero lejos de ser perfecto. Los datos tienen poca señal, y el código no puede inventar la que no hay.

Palabras que se repiten

Variable (o característica, o feature)
Una columna de la tabla que describe al cliente: edad, ingresos, saldo promedio, región.
Objetivo (o target)
La columna objetivo: 1 si el cliente convirtió ese mes, 0 si no. Es lo que se quiere predecir.
Entrenamiento, validación y test
Entrenamiento: datos con respuesta que el modelo usa para aprender. Validación: datos con respuesta que se separan para comprobar qué tan bien aprendió. Test: datos sin respuesta, los de la competencia.
Fuga de datos (data leakage)
Cuando, sin querer, el modelo ve información que no tendría en la vida real. Hace que las pruebas den resultados espectaculares y que luego el rendimiento real sea malo. Casi todo el cuidado del código existe para evitarla.
Sobreajuste (overfitting)
Cuando el modelo memoriza los ejemplos de entrenamiento, incluido su ruido, y falla con datos nuevos.

Cuatro palabras de Python que vas a ver

def nombre(...)
Define una función: una receta con nombre que recibe datos y devuelve un resultado.
class Nombre
Define una clase: un molde para crear objetos que guardan datos y tienen funciones propias (llamadas métodos).
DataFrame (df, X)
Una tabla con filas y columnas, como una hoja de Excel dentro del programa. Es el tipo de dato de la librería pandas.
cfg.algo
Un valor guardado en la configuración (Sección 0). El punto significa "dentro de".

Lo que se descubrió al revisar los datos

  • Hay 24.628 clientes distintos en train. Un cliente aparece 4,5 veces en promedio (entre 1 y 11).
  • Cerca del 15 % de las filas son conversiones, y ese porcentaje es muy estable de un mes a otro.
  • Un cliente que convierte no vuelve a aparecer en meses posteriores (se comprobó: 0 filas después de la conversión).
  • El 81 % de los clientes de diciembre ya tenía historial en train.
  • De todas las variables, solo dias_ultima_interaccion cambia de un mes a otro para un mismo cliente (en el 80 % de los que aparecen más de una vez). Las demás son fijas.
Cuidado

Que casi todas las variables sean fijas por cliente tiene una consecuencia importante: gran parte de las variables históricas que crea el código (rezagos, promedios móviles) son copias del valor actual y no aportan información nueva. El código las detecta y las descarta en la Sección 3.

Sección 0 del código

Configuración

Aquí está Config, una "hoja de ajustes". Cada número que podría querer cambiarse (cuántos meses se validan, cuántas variables se conservan, cuántas pruebas hace Optuna) vive en este lugar y no repartido por el programa. Si quieres cambiar el comportamiento, casi siempre se edita aquí o se usa un argumento al ejecutar.

lags: Tuple[int, ...] = (1, 2, 3)     # rezagos: 1, 2 y 3 meses atrás
ventana: int = 3                      # ventana móvil de 3 meses
umbral_ohe: int = 10                  # hasta 10 categorías: One-Hot; más: Target Encoding
suavizado_te: float = 50.0            # fuerza del suavizado del Target Encoding
corr_umbral: float = 0.95             # correlación máxima permitida entre variables
top_k: int = 80                       # máximo de variables a conservar
n_meses_validacion: int = 3           # meses finales de train que se usan para validar
n_trials_optuna: int = 30             # pruebas del buscador de hiperparámetros
n_seeds_final: int = 3                # semillas que se promedian al final
seed: int = 42                        # semilla base, para repetir resultados
Analogía

Es el panel de una lavadora: la máquina hace todo sola, pero antes eliges temperatura, centrifugado y duración. Config son esos botones.

También guarda los nombres de las columnas exactamente como los describe el archivo de documentación: qué columnas son numéricas, cuáles de sí o no, cuáles de texto, y sobre cuáles se calculan rezagos y promedios móviles. El código no usa ninguna columna que no esté descrita en esos documentos.

¿Qué es la "semilla"?

Muchos pasos usan azar (qué filas se muestrean, cómo empieza a construir árboles el modelo). La semilla fija ese azar para que, si ejecutas el programa dos veces, obtengas el mismo resultado.

Sección 1 del código

Carga, validación y diagnóstico

Antes de construir nada se lee la información y se comprueba que sea la esperada. Son cuatro funciones pequeñas.

optimizar_memoria

Por defecto, pandas guarda cada número con mucho espacio, aunque sea un 7. Esta función le pide a cada columna que use el tamaño mínimo que le alcance: los enteros se encogen y los decimales pasan a float32 (precisión más que suficiente aquí). Con los datos de la competencia, train ocupa 34,5 MB en memoria.

for c in df.select_dtypes(include="integer").columns:
    df[c] = pd.to_numeric(df[c], downcast="integer")
for c in df.select_dtypes(include="floating").columns:
    df[c] = df[c].astype("float32")

Con 110 mil filas no sería imprescindible, pero el mismo código sirve para tablas veinte veces más grandes sin quedarse sin memoria RAM.

cargar_datos

Lee train.csv y test.csv con pd.read_csv, les aplica la optimización anterior y avisa en pantalla de cuántas filas y columnas llegaron.

validar_esquema

Es el control de calidad. Detiene el programa con un mensaje claro si:

  • falta alguna columna de las que describe la documentación,
  • hay filas repetidas para el mismo cliente en el mismo mes (el cálculo de rezagos supone que no las hay),
  • la lista de rezagos no incluye el rezago 1.

Si encuentra celdas vacías no se detiene, solo avisa, porque la documentación dice que no debería haber ninguna.

diagnostico_inicial

No modifica nada. Solo imprime hechos que ayudan a entender el problema: la tasa de conversión de cada mes, cuántas filas aparecen después de que el cliente ya convirtió (debe ser 0), qué porcentaje de los clientes de test tiene historial en train (81 %) y cuántas categorías tiene cada variable de texto. Es el equivalente a mirar los datos antes de decidir qué hacer con ellos.

Sección 2 del código

Ingeniería de características

"Ingeniería de características" significa crear variables nuevas que le den al modelo pistas que la tabla original no muestra de forma directa. La idea principal es usar el historial: no solo cómo está un cliente este mes, sino cómo venía los meses anteriores.

preparar_base: juntar y ordenar

Une train y test en una sola tabla y la ordena por cliente y por mes. Se juntan para que diciembre (test) pueda "mirar atrás" a noviembre y a meses anteriores del mismo cliente. Esto no es trampa, porque las variables de noviembre se conocen en diciembre. La columna objetivo de test se rellena con vacío y nunca se usa.

df = pd.concat([tr, te], ignore_index=True)
df = df.sort_values([cfg.id_col, cfg.mes_col], kind="mergesort").reset_index(drop=True)
df["_mes_idx"] = (df[cfg.mes_col] // 100) * 12 + (df[cfg.mes_col] % 100)

Se añaden tres columnas auxiliares que empiezan con guion bajo:

  • _es_test: marca las filas de diciembre.
  • _orden_test: la posición original de cada fila de test, para devolver las predicciones en el mismo orden al final.
  • _mes_idx: convierte el mes en un número corrido. 202611 pasa a 2026 × 12 + 11 = 24323 y 202612 pasa a 24324. Así restar dos meses da la distancia real, también entre diciembre y enero (202701 es 24325).

crear_features_temporales: rezagos y ventanas

Este es el corazón de la sección. Crea cuatro tipos de variables nuevas:

TipoNombre de ejemploQué significa

Los rezagos (1, 2 y 3 meses) y los cambios se calculan para 7 variables: saldo_promedio, ingresos, dias_ultima_transaccion, ratio_deuda_ingresos, numero_productos, visitas_web_ultimos_90_dias y dias_ultima_interaccion. Los promedios y sumas móviles se calculan para 5 de ellas. En total son 39 columnas nuevas, más una llamada meses_en_ventana3 que dice cuántos de esos 3 meses existen realmente.

El detalle que lo hace correcto: los rezagos respetan el calendario

Un cliente no aparece todos los meses. Si se tomara simplemente "la fila anterior", un rezago de 1 mes podría traer el valor de hace 3 meses sin que nadie se dé cuenta. El código comprueba que la fila anterior sea exactamente el mes esperado; si no lo es, deja el valor vacío.

# ¿la fila k posiciones atrás es exactamente k meses antes?
mascara = (df["_mes_idx"] - grupo_mes.shift(k)) == k
lag = np.where(mascara, valor_k_filas_atras, np.nan)
Cuidado

Todas estas variables miran solo hacia atrás. Nunca se usa información de meses posteriores, porque en la vida real no existe cuando se hace la predicción. Eso es evitar la fuga de datos.

target_encoding_temporal: convertir texto en números sin hacer trampa

Los modelos solo entienden números, así que las variables de texto hay que convertirlas. Hay dos técnicas, y el código elige según cuántas categorías tenga cada variable (el umbral es umbral_ohe = 10):

One-Hot Encoding (pocas categorías)

Crea una columna de 0 y 1 por categoría. banda_riesgo se convierte en banda_riesgo_low, banda_riesgo_medium y banda_riesgo_high; un cliente de riesgo medio tendrá 0, 1, 0.

Target Encoding (muchas categorías)

Reemplaza cada categoría por la tasa de conversión histórica de esa categoría. Sirve cuando hay cientos de valores y crear una columna por cada uno sería inmanejable.

El Target Encoding tiene un riesgo enorme de fuga: si la tasa de una categoría se calcula con todos los datos, incluida la fila que se está describiendo, el modelo "ve" la respuesta. Por eso aquí se calcula con corte temporal: para una fila del mes M solo se usan los resultados de meses anteriores a M.

# fórmula (m = suavizado_te = 50)
TE = (S + tasa_global * m) / (N + m)
# S = conversiones de esa categoría en meses anteriores
# N = filas de esa categoría en meses anteriores

El suavizado (m) evita extremos: una categoría con 3 filas y 1 conversión no recibe una tasa de 33 %, sino una cercana a la tasa global. Las filas de diciembre usan todo train. El primer mes de train no tiene pasado y queda vacío.

Analogía

Es como estudiar para un examen con exámenes de años anteriores. Si entre tus apuntes está el examen de este año con las respuestas, sacarás 10 y no habrás aprendido nada. El corte temporal garantiza que solo se estudia con lo que ya había pasado.

En estos datos no se activa: las 5 variables de texto tienen entre 3 y 5 categorías, así que todas usan One-Hot. El mecanismo está construido y comprobado (se recalculó a mano una fila y coincidió), por si en otra competencia aparece una variable con muchas categorías. Se puede forzar con --umbral-ohe 4.

Sección 3 del código

Selección de características

Tener más variables no siempre ayuda. Las repetidas o inútiles agregan ruido, hacen más lento el entrenamiento y facilitan el sobreajuste. Esta sección aplica tres filtros en cadena. Cada uno es una clase con dos acciones: fit (decide qué conservar mirando los datos) y transform (aplica esa decisión).

Filtro 1 · SelectorVarianzaCero

Elimina las columnas que tienen un único valor en todas las filas. Una columna que nunca cambia no puede distinguir a un cliente de otro.

n_unicos = X.nunique(dropna=True)
self.cols_constantes_ = n_unicos[n_unicos <= 1].index.tolist()

Resultado real: elimina 6 columnas, todas del tipo …_delta1 (cambio mensual de saldo, ingresos, productos, etc.). Salen constantes en 0 porque esas variables no cambian entre meses, lo que confirma lo que se vio en los datos.

Filtro 2 · SelectorCorrelacion

Dos columnas con una correlación de Pearson mayor a 0,95 dicen casi lo mismo (por ejemplo, saldo_promedio y su rezago de 1 mes cuando el saldo no cambia). Se conserva una y se elimina la otra, siempre la que más se parece al resto. Para ir rápido calcula las correlaciones con una muestra de hasta 50.000 filas.

corr = muestra.corr(method="pearson").abs()

Resultado real: elimina 22 columnas. Son grupos de variables que repiten lo mismo (la variable original, sus rezagos y su promedio móvil); de cada grupo se conserva una.

Analogía

Si tienes una balanza en kilos y otra en libras, no necesitas las dos para saber cuánto pesa algo.

Filtro 3 · SelectorImportanciaLGBM

Entrena un LightGBM rápido (300 árboles) con las variables que sobrevivieron y mide cuánto aportó cada una a las decisiones del modelo (la "ganancia"). Conserva las 80 más importantes.

modelo = lgb.LGBMClassifier(n_estimators=300, learning_rate=0.05, ..., importance_type="gain")

seleccionar_features: la cadena completa

Ejecuta los tres filtros en orden y devuelve la lista final de nombres. Un punto esencial: se ajusta solo con los meses de entrenamiento, nunca con los de validación. Si no, la variable elegida habría "visto" los meses con los que luego se evalúa y la nota saldría inflada.

Cuidado al interpretar

Entre las más importantes aparecen nombres como numero_productos_roll3_mean. Como esa variable casi no cambia en el tiempo, su promedio móvil vale prácticamente lo mismo que el valor original, y el modelo eligió una de las dos copias. No significa que "el promedio de 3 meses" sea especial. Las señales que más pesan son el número de productos, los días desde la última transacción, la banda de riesgo y el ratio deuda/ingresos.

Sección 4 del código

Modelado y validación

Con las variables listas, se entrenan varios modelos y se mide cuál ordena mejor a los clientes. La sección 'Los modelos, uno por uno' (más abajo) explica cada modelo; aquí se explica cómo está montada la comparación.

Cómo se parte la información: validación temporal

Para saber si un modelo funciona hay que probarlo con datos que no vio. El código reserva los últimos 3 meses de train (septiembre a noviembre) para validar y entrena con enero a agosto:

Entrenamiento

Enero a agosto
80.300 filas (73 %)

Validación

Septiembre a noviembre
29.800 filas (27 %)

Es casi el 70/30 clásico, pero cortado por el calendario y no al azar. Esto no es un capricho. Se midió con el mismo modelo y las mismas variables:

Forma de partir los datosGini
Aleatoria 70/30 (train_test_split)0,259
Aleatoria por cliente 70/300,268

La partición aleatoria da una nota más alta, y esa nota es engañosa: un mismo cliente aparece en varios meses casi sin cambiar, así que con un corte al azar el modelo ya "conoce" a los clientes de la prueba. La competencia, en cambio, evalúa un mes futuro. La partición por calendario imita eso. Validar con 3 meses en vez de 1 baja el margen de error de la nota de ±0,017 a ±0,010 de Gini.

construir_modelo: la fábrica

Una sola función que, dado el nombre de una familia ("lightgbm", "xgboost", "catboost", "random_forest") y sus ajustes, devuelve el modelo listo para entrenar. Así el resto del programa no repite código por cada modelo, y agregar uno nuevo (como se hizo con CatBoost) toca pocos lugares. Aquí también viven los ajustes por defecto de cada modelo (PARAMS_DEFECTO) y dos constantes: un máximo de 2000 árboles y una paciencia de 100 para el early stopping.

EvaluadorModelos: el cuaderno de notas

Es una clase que recibe las tablas de entrenamiento y validación y se encarga de todo lo demás:

MétodoQué hace
entrenar_lightgbm, entrenar_xgboost, entrenar_catboost, entrenar_random_forestEntrena ese modelo con los datos de entrenamiento y lo evalúa con los de validación

auc = roc_auc_score(y_true, y_prob)
return auc, 2 * auc - 1        # (AUC, Gini)

Early stopping: saber cuándo parar

Los modelos de boosting suman árboles de a uno. Cada árbol nuevo mejora el entrenamiento, pero llega un punto en que empieza a memorizar y la validación deja de mejorar. El early stopping vigila el AUC de validación y, si pasan 100 árboles seguidos sin mejora, se detiene y se queda con el mejor momento.

m.fit(self.X_train, self.y_train, eval_set=[(self.X_val, self.y_val)], eval_metric="auc",
      callbacks=[lgb.early_stopping(ES_ROUNDS, verbose=False)])
Analogía

Es dejar de estudiar cuando los simulacros dejan de mejorar. Estudiar más solo te hace memorizar las preguntas de los simulacros.

Optuna: probar ajustes de forma inteligente

Cada modelo tiene "perillas" (hiperparámetros): cuántas hojas por árbol, qué velocidad de aprendizaje, cuánta regularización. Optuna no es un modelo; es un buscador que prueba combinaciones de perillas (30 por defecto) y aprende de las anteriores para elegir mejor las siguientes. Se aplica a LightGBM y el resultado aparece como una fila aparte, LightGBM_Optuna.

learning_rate    = trial.suggest_float("learning_rate", 0.01, 0.1, log=True)
num_leaves       = trial.suggest_int("num_leaves", 8, 256, log=True)
min_child_samples = trial.suggest_int("min_child_samples", 10, 300, log=True)
# ... y subsample, colsample_bytree, reg_alpha, reg_lambda
Cuidado

Tanto el early stopping como Optuna usan los meses de validación para decidir. Por eso las notas del reporte son ligeramente optimistas respecto a lo que se obtendrá en la competencia. Es la misma ventaja para todos los modelos de boosting, así que la comparación entre ellos es justa.

Sección 5 del código

Entrenamiento final y entrega

Ya se sabe qué modelo ordena mejor. Falta producir la predicción de diciembre.

entrenar_y_predecir_final

Reentrena el modelo ganador con el 100 % de train (enero a noviembre), porque con más datos aprende mejor, y predice test. Dos decisiones merecen explicación:

  • Cuántos árboles. El early stopping ya no se puede usar, porque no queda un conjunto de validación. Se toma el número de árboles que resultó óptimo y se multiplica por la proporción de datos extra. Con 110.100 filas frente a 80.300, el factor es ≈ 1,37. 
    n_iter = max(10, int(round(mejor_iter * factor_datos)))
  • Varias semillas. Se entrena el modelo 3 veces con semillas distintas y se promedian las predicciones. Un modelo depende un poco del azar; el promedio es más estable que cualquiera de las tres.

Al final las probabilidades se recortan al rango de 0 a 1 por seguridad.

Sección 6 del código

El programa principal

La función main no hace cálculos propios. Llama en orden a todas las anteriores. Leerla es el mejor resumen de todo el proyecto:

  1. Cargar y comprobar los archivos, e imprimir el diagnóstico (Sección 1).
  2. Crear las variables (Sección 2).
  3. Partir por calendario en entrenamiento (enero a agosto) y validación (septiembre a noviembre).
  4. Seleccionar variables usando solo el entrenamiento (Sección 3).
  5. Comparar modelos y quedarse con el de mayor Gini (Sección 4).
  6. Reentrenar con todo, predecir y exportar (Sección 5).
  7. Guardar archivos de trazabilidad junto al submission.

Cómo se ejecuta

python pipeline.py --datos ./data --salida ./salida/submission.csv --trials 30

Los argumentos (--datos, --salida, --trials, --meses-val, --top-k, --umbral-ohe, --n-seeds, --semilla) son la forma de cambiar la configuración sin tocar el código. Su detalle está en el README.md del proyecto. Con --trials 0 se omite Optuna y la ejecución es mucho más rápida. En total tarda alrededor de 2 minutos.

Parte aparte

Los modelos, uno por uno

El programa compara cuatro modelos. Los cuatro hacen lo mismo en esencia (reciben las variables de un cliente y devuelven una probabilidad) y los cuatro están construidos con árboles de decisión. Lo que cambia es cómo combinan esos árboles.

La pieza base: el árbol de decisión

Un árbol es una cadena de preguntas de sí o no que va separando a los clientes en grupos. Por ejemplo: "¿Tiene más de 3 productos? Si sí, ¿su riesgo es bajo? …". Cada grupo final (una hoja) recibe la tasa de conversión de los clientes que cayeron en él. Un árbol solo es fácil de entender, pero impreciso y muy sensible a los detalles. La fuerza viene de juntar muchos.

Dos formas de juntar árboles

Bosque (bagging): en paralelo

Árbol 1Árbol 2Árbol 3…→promedio

Muchos árboles se entrenan de forma independiente, cada uno con una muestra distinta de filas y columnas. Al final votan y se promedian sus resultados. Los errores individuales tienden a cancelarse.

Boosting: en serie

Árbol 1→corrige 1→corrige 2→suma

Los árboles se entrenan uno tras otro. Cada nuevo árbol se concentra en los errores que dejó el conjunto anterior. La predicción final es la suma de todas las correcciones, cada una multiplicada por una "velocidad de aprendizaje" pequeña.

Analogía

Bosque: pedirle su opinión a 300 personas que no se hablan entre sí y quedarte con el promedio. Boosting: un equipo donde cada persona revisa el trabajo de la anterior y arregla solo lo que quedó mal.

Random Forest

Bosque Es el representante del bagging. En el código usa 300 árboles, exige al menos 20 clientes por hoja, en cada división solo considera una parte de las columnas (la raíz cuadrada del total) y cada árbol entrena con el 70 % de las filas.

  • Fortalezas: muy difícil de estropear, casi no necesita ajuste, resiste bien el ruido.
  • Debilidades: suele quedar por debajo del boosting cuando hay patrones sutiles; es el más lento aquí (unos 20 segundos frente a 2 a 5 de los otros). Como versiones antiguas de scikit-learn no admiten datos vacíos, el código los rellena con la mediana antes de entrenarlo.

LightGBM

Boosting De Microsoft. Está diseñado para ser muy rápido: agrupa los valores numéricos en "cajones" (histogramas) antes de buscar los cortes, y hace crecer cada árbol por hoja, es decir, siempre divide la hoja que más reduce el error, sin importar a qué nivel esté. Eso lo hace eficaz, pero con riesgo de árboles muy desparejos si no se limita el número de hojas.

  • Ajustes principales en el código: 31 hojas por árbol, velocidad de aprendizaje 0,03, mínimo de 50 clientes por hoja, 80 % de filas y 70 % de columnas por árbol.
  • Fortalezas: velocidad, buen rendimiento con tablas grandes, gran cantidad de ajustes disponibles.
  • Es el modelo que se ajusta con Optuna y el que ganó la comparación.

XGBoost

Boosting El modelo que popularizó el boosting en competencias. También usa histogramas, pero hace crecer el árbol por niveles: divide todas las hojas de un nivel antes de pasar al siguiente, hasta una profundidad máxima. Tiene regularización incorporada para frenar el sobreajuste.

  • Ajustes principales en el código: profundidad máxima 6, velocidad de aprendizaje 0,03, peso mínimo por hoja 5.
  • Fortalezas: muy probado, estable, buen control del sobreajuste.
  • Debilidades: históricamente algo más lento que LightGBM; árboles por niveles pueden ser menos flexibles.

CatBoost

Boosting De Yandex. Dos rasgos lo distinguen. Primero, sus árboles son simétricos: en cada nivel se usa la misma pregunta para todas las ramas, lo que da árboles más simples y más resistentes al sobreajuste. Segundo, está pensado para tratar variables de texto directamente, con técnicas que evitan la fuga de datos al codificarlas.

  • Ajustes principales en el código: profundidad 6, velocidad de aprendizaje 0,05, regularización L2 de 3.
  • Fortalezas: buen rendimiento sin ajustar casi nada, estable.
  • Aquí no aprovecha su mayor ventaja: las variables de texto ya llegan convertidas a 0 y 1 (One-Hot), así que corre como cualquier otro modelo de árboles.

Por qué dan casi lo mismo

Entre el mejor y el peor hay 0,01 de Gini, y la nota tiene un margen de error de unos ±0,010. Es decir, la diferencia entre modelos no se distingue del ruido. Hay tres razones razonables:

  • La señal que hay en los datos es limitada, y cualquier modelo decente la encuentra.
  • Casi todas las variables son fijas por cliente, así que hay poca información extra que un modelo más sofisticado pueda aprovechar.
  • Son modelos de la misma familia (árboles), con la misma materia prima.

Que gane LightGBM + Optuna se debe en parte a que es el único al que se le buscaron ajustes de forma activa. Habría que dar el mismo trato a los otros para una comparación estrictamente igualitaria.

¿Cuál usar?

El programa elige automáticamente al de mayor Gini en validación, y ese es el que se reentrena con todo para la entrega. En la práctica, cualquiera de los tres de boosting es una elección defendible aquí. Lo que más movería el resultado no es cambiar de modelo, sino conseguir variables con más información sobre el cliente.

Parte final

Glosario

AUC
Área bajo la curva ROC. Probabilidad de que el modelo ponga a un cliente que convirtió por encima de uno que no. 0,5 es azar; 1 es perfecto.
Gini
2 × AUC − 1. Es el AUC reescrito para que el azar valga 0. La métrica de la competencia.
Bagging
Entrenar muchos modelos independientes con muestras al azar y promediarlos. Es la idea del Random Forest.
Boosting
Entrenar modelos en serie, cada uno corrigiendo los errores del conjunto anterior. Es la idea de LightGBM, XGBoost y CatBoost.
Early stopping
Detener el entrenamiento cuando la validación deja de mejorar durante un número de rondas.
Fuga de datos (leakage)
Que el modelo use información que no tendría al predecir en la vida real. Infla las pruebas y arruina el resultado real.
Hiperparámetro
Un ajuste del modelo que se decide antes de entrenar (profundidad, velocidad de aprendizaje). No lo aprende el modelo.
Importancia de variables
Medida de cuánto contribuyó cada variable a las decisiones del modelo.
One-Hot Encoding
Convertir una categoría en varias columnas de 0 y 1, una por valor posible.
Optuna
Librería que busca automáticamente buenos hiperparámetros probando combinaciones.
Pearson (correlación)
Número entre −1 y 1 que dice cuánto se mueven juntas dos columnas. Cerca de ±1 significa que dicen casi lo mismo.
Rezago (lag)
El valor de una variable en un mes anterior.
Semilla (seed)
Número que fija el azar para que los resultados se puedan repetir.
Sobreajuste (overfitting)
Cuando el modelo memoriza el entrenamiento y falla con datos nuevos.
Target Encoding
Reemplazar una categoría por la tasa histórica del objetivo en esa categoría. Requiere cuidado temporal para no filtrar la respuesta.
Validación temporal
Separar entrenamiento y validación por fecha, entrenando con el pasado y evaluando con el período siguiente.
Ventana móvil (rolling)
Un cálculo (promedio, suma) sobre los últimos N meses.
